# Launch plan: working toward 4,000 stars

4,000 stars is an aspiration, not a forecast. This plan is a proposed experiment, not evidence of demand.

## Make the value visible

1. Run the skill on a small app you own with a genuinely broken mobile journey.
2. Capture the original failure, the prompt, the repair, and successful browser verification.
3. Record a short demo showing the actual result. Add it near the top of the README.
4. Repeat on a second app with a different defect. Document what did not work too.

## Publish a useful first release

Create a public repository named `website-rescue`, upload this package, and check the installation instructions from a clean setup. Add the real demo and an accurate release description. Do not publish simulated results as real evidence.

Suggested repository description:

> A Codex skill that reproduces website bugs, fixes them, and verifies the result with before-and-after evidence.

Suggested launch copy, after the demo has been verified:

> I built Website Rescue, a Codex skill for repairing broken website journeys. It reproduces the issue, changes the code, and checks the result. Here's a real before-and-after demo. I'd love reproducible examples where it fails so I can improve it.

## Learn from actual users

Start with five people who have existing website projects. Track whether they can install it, get a useful repair, and understand the evidence. Fix repeated friction before adding features.

Share a real demo in communities where you already participate and where project sharing is welcome. Follow community rules. Avoid unsolicited bulk messages, bought stars, or engagement exchanges.

Track weekly: successful first uses, reproduced issue reports, repeat users, contributions, and GitHub stars. Use 100, 500, 1,000, and 4,000 stars as review points, with no promised timeline. If attention does not translate into useful repairs, improve the skill and demo before widening promotion.
